# 头脑风暴：跨 IDE Agent 通信，到底值不值得做

## 1. 先给判断

**想法成立，但要换一个心智模型。**

「让三个工具通过加载 skill 就自动广播、互相发现」这个描述里，藏着一个错误假设：
把 skill 当成了**会自动运行的程序**。实际上 skill 只是一段被注入上下文的指令，
加载 ≠ 执行 ≠ 常驻。所以：

- 能做成的：一份共享协议 + 一个共享目录 + 三端各注入一条「上线」指令
   → Agent 在会话开始时注册、发现、收发结构化消息
- 做不成的：三个 IDE 后台自动组网、实时互推、一方不在线也能即时响应

一旦把目标从「自动组网」改成「**异步信箱 + 显式上线**」，整件事立刻可落地，
而且不需要任何一家的私有 API。这也是本 skill 采用的实现。

## 2. 最反直觉的一点：通信不是瓶颈

三个 IDE 打开同一个仓库时，**文件本来就是共享的**。A 写的代码 B 立刻能看到，
甚至不需要发消息。所以「让它们能传数据」几乎没有新增价值。

真正稀缺的是另外三样东西：

| 稀缺物 | 文件共享解决不了的原因 |
|--------|------------------------|
| **上下文隔离** | A 不知道 B 在改什么、为什么改、改到哪一步了；git diff 只有结果没有意图 |
| **角色与分工** | 谁负责前端、谁负责后端、谁做验收，没有显式约定就会互相覆盖 |
| **交接时序** | B 必须等 A 的 API 定完才能动手，文件存在 ≠ 可以开始 |

所以总线的正确定位不是「传文件」，而是**传契约**：
意图、边界、验收标准、完成回执。这也解释了为什么本 skill 强制 `body` 用
`intent / request / acceptance` 这种结构，而不是自由文本。

> 推论：如果三个 Agent 只是各写各的、互不依赖，那这个总线就是纯 overhead，别用。

## 3. 传输层选型对比

| 方案 | 跨工具通用性 | 实时性 | 跨机器 | 部署成本 | 适用 |
|------|--------------|--------|--------|----------|------|
| **共享文件总线（本 skill）** | 极高 | 异步 | 否 | 零 | 单机 MVP、验证想法、可人工排查 |
| 本地 HTTP/WS 中继 | 中（各端要能发请求） | 准实时 | 局域网 | 需常驻进程 | 需要推送、需要在线状态精确 |
| **同一远端 MCP server** | 高（三端普遍支持 MCP） | 准实时 | 是 | 需部署 + 鉴权 | 最「正规」的演进方向 |
| Git 分支当总线 | 高 | 很慢 | 是 | 低 | 异地异步协作、天然留痕与冲突检测 |
| 智能体邮箱 / 邮件 | 低（生态绑定） | 异步 | 是 | 需账号 | 跨组织、有人参与的审批流 |
| 共享数据库 / Redis | 中 | 实时 | 是 | 高 | 多 Agent 高频协作、任务队列 |

**推荐路径**：先用文件总线把协议和交互语义跑通（本 skill），
确认「契约式交接」真的有用之后，再把 `deliver()` / `active_peers()` 换成远端 MCP，
上层消息 schema 一行不改。反过来先搭中继，很可能最后发现协议设计得不对。

注意 MCP 的定位：它是**单个宿主进程内**的工具协议，三个 IDE 各自连同一个
MCP server 时才构成跨 IDE 通道——不是「MCP 天然能让 IDE 互通」。

## 4. 值得做的场景

- **异构能力分工**：Qoder 写 Spring Boot 接口、Trae 写 React 页面、WorkBuddy
  做调研/文档/编排。三端模型与上下文不同，分工有真实收益。
- **契约先行**：一端先发布 `body.request` 里的接口契约，另一端据此并行开发，
  完成后用 `reply` 回传改动清单与校验结果。
- **竞争式任务队列**：把任务 `--to '*'` 广播出去，靠 `claim` 的原子性保证
  **只有一个 Agent 领到**。这比指定执行者更优雅，也不需要中心调度器。
- **上下文续接**：一个 IDE 会话上下文快满了，把当前状态写成结构化消息，
  另一个 IDE 的新会话 `claim` 后接着做。
- **人工可审计的协作**：`outbox/` + `events.log` 让「谁在什么时候让谁做了什么」
  一目了然，比散落在三个聊天窗口里的记录强得多。

## 5. 伪需求 / 别踩的坑

- 「让三个工具互相聊天」——没有交付物的通信没有价值
- 「加载 skill 就自动组网」——做不到，必须接受显式上线或在宿主侧配启动钩子
- 「实时等对方回复」——会话式 Agent 没有常驻循环，只会异步轮询
- 「广播给所有工具」——广播实际是遍历注册表单播，离线收不到、高频会堆积
- 「把整份代码塞进消息」——64 KB 上限，且三个 IDE 本来共享文件，传路径即可
- 「三端同时改同一批文件」——总线的 `claim` 只保证消息不重复领，
  **不保证文件不冲突**，必须靠 `constraints` 划清所有权

## 6. 三个更激进的延伸

1. **共享黑板（blackboard）**：除了点对点消息，再加一份所有 Agent 共同读写的
   `board.json`（当前架构决策、已占用文件、进行中的任务）。它比 N×N 消息更省，
   但引入写冲突，需要单写者或 CAS。适合作为 v2。
2. **能力路由**：`capabilities` 目前只是标签。可以加一个 `send --cap frontend`
   让 CLI 自动挑选最匹配的在线 peer，把「发现」升级成「调度」。
   风险是标签不可信、且能力会随模型/上下文变化。
3. **任务 DAG 与验收闭环**：给消息加 `depends_on` 和 `acceptance`，
   让 orchestrator 按依赖图派发、收集 `reply` 并判定是否通过。
   这时总线才真正接近「多 Agent 编排系统」，但复杂度也上一个台阶。

## 7. 演进路线

| 阶段 | 目标 | 完成标志 |
|------|------|----------|
| v0（已实现） | 单机文件总线、协议与 CLI、三端注入说明 | 三端 `doctor` root 一致，能跑通注册→委派→回执 |
| v1 | 真实项目里跑一轮契约式交接 | 有一份「发送的任务 / 收到的结果 / 用户验收」记录 |
| v2 | 共享黑板 + 能力路由 + 幂等处理 | 多任务并行不冲突、不重复执行 |
| v3 | 换成远端 MCP / 网络中继 | 跨机器可用，**同时补齐签名与鉴权** |

v3 的鉴权不是可选项：一旦总线目录/服务暴露到网络，
任何能写它的人都能伪造消息要求别的 Agent 干活，见 [security.md](security.md)。

## 8. 已知限制（说在前面）

- 单机、共享文件系统；跨机器直接失效
- 无身份鉴别、无消息签名，`registry/` 可被手工伪造
- 无实时推送，在线状态靠心跳 + TTL，最长有 TTL 的判定延迟
- 消息乱序：同秒消息按 uuid 排序，`poll` 只是近似时间序
- 崩溃恢复依赖 `purge` 重新投递，处理逻辑必须幂等
- 三端 skill/rules 机制不统一，注入层需各自配置，且随工具版本变化
- 三个大模型同时跑在同一仓库会带来 token 成本与文件竞争，通信本身不产生收益

## 9. 最小演示（不接任何 IDE）

两个终端各模拟一个 Agent，先验证总线本身：

```bash
export AGENT_BUS_ROOT="$(mktemp -d)/bus"
export AGENT_BUS_CLI="<SKILL_DIR>/scripts/agent_bus.py"
python "$AGENT_BUS_CLI" doctor

# 终端 B：先上线
python "$AGENT_BUS_CLI" register --id trae@demo-b --tool trae --caps frontend

# 终端 A：注册、发现、派活
python "$AGENT_BUS_CLI" register --id workbuddy@demo-a --tool workbuddy --caps docs
python "$AGENT_BUS_CLI" discover
python "$AGENT_BUS_CLI" send --from workbuddy@demo-a --to trae@demo-b \
  --type task --subject "写登录页" \
  --body '{"intent":"登录表单","request":{"constraints":["只改 src/ui/**"]},"acceptance":["build 通过"]}'

# 终端 B：收取
python "$AGENT_BUS_CLI" poll --id trae@demo-b
python "$AGENT_BUS_CLI" claim --id trae@demo-b
python "$AGENT_BUS_CLI" ack --id trae@demo-b --msg-id <上一步返回的 id> \
  --reply-json '{"status":"done","files":["src/ui/Login.tsx"]}'

# 回到终端 A
python "$AGENT_BUS_CLI" poll --id workbuddy@demo-a
```
