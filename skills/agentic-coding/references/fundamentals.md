# Fundamentals — 概念、循环与术语

> 本文件是**概念、核心循环、术语与固有局限的唯一事实源**。SKILL.md 与其他文件只引用本节定义，不另写一套模型或术语表。

## 1. 定义

Agentic coding（智能体编程 / 代理式编码）是一种软件开发方式：AI agent 接收一个高层目标，自主拆解步骤、修改代码、执行程序、读取输出、按结果迭代，直到目标达成或需要人工介入，期间无需人逐步指挥每一步。

一句话区分：从 *AI completes my next line* 到 *AI completes my next task* —— 从按键级辅助变成任务级委派。

工程师的工作从「执行」转为两件事：**写清任务规格** 与 **审查产物**。

## 2. 与传统 AI 辅助编码的对比

| 维度 | 传统辅助（补全 / 内联聊天） | Agentic coding |
| --- | --- | --- |
| 触发 | 实时按键、单次提问 | 自然语言的任务描述 |
| 作用域 | 下一行、单个函数、单个文件 | 多文件、多步骤、完整特性或重构 |
| 人的参与 | 持续，逐条接受或拒绝 | 首尾两端，中途仅在检查点介入 |
| 自我纠错 | 无，不验证自己的建议 | 内建，跑测试并按失败迭代 |
| 单次时长 | 秒级 | 分钟到小时级 |
| 交付物 | 代码片段 / 回答 | diff、PR 或可审查的变更集 |

## 3. 核心循环（六步模型）

所有实现（无论厂商）都运行同一循环的变体：

1. **Goal** — 人给出目标与足够上下文。
2. **Plan** — 读取相关文件，判断改动点，形成方案并拆成子任务。
3. **Execution** — 调用工具：读写文件、执行 shell 命令、调用 API、检索代码、必要时操作浏览器。
4. **Reflection / verification** — 运行编译、测试、lint，读取报错，判断完成度。
5. **Iteration** — 依据第 4 步调整方案并重复，直到通过或达到重试上限。
6. **Output** — 以 diff / PR / 摘要形式交付，人审查后决定合并。

Goal 与 Output 是**人在两端**，中间四步由 agent 循环，因此常被概括为「规划 → 执行 → 验证 → 迭代」四阶段；本 skill 一律以本节**六步模型**为准，避免同一循环出现两套表述。

第 3 与第 4 步并非严格线性，agent 常在「写一点、测一点」之间反复切换。把上述步骤串成循环而非一次性请求-响应的控制流称为 **orchestration**，内部多采用 ReAct 或类似策略。

## 4. 四个必要前提

1. **工具与执行环境** — 文件系统读写、shell、代码检索 / LSP、浏览器。纯聊天模型没有工具就无法形成 agentic 循环。
2. **编排** — 规划 → 工具调用 → 观察 → 再决策的控制流，以及重试用例、代价预算、终止条件。
3. **上下文与记忆** — 长上下文窗口、项目约定文件（如 CLAUDE.md、规则文件）、通过 MCP 等协议接入外部数据源与工具。每轮工具输出都消耗 token，长任务会挤出早期决策；上下文的取舍与摘要是实际工程问题，不是事后优化。
4. **可验证反馈** — 编译器、测试、lint、截图、运行结果。这是自我纠错唯一的现实依据，也是区分「agentic」与「多轮聊天」的硬指标。

## 5. 为什么近两年才可行

长上下文与推理能力提升、稳定的工具调用 / function calling、以及 MCP 这类工具接入的开放标准，使「给模型一个目标 + 一套工具 + 一个循环」成为可落地的工程架构。突破点不是更好的补全模型，而是**让模型使用工具并读取结果**。

## 6. 工具与工作流形态（截至 2026-11 的快照）

> 本节是**时效性快照**，不是事实源。工具与产品形态演进很快，选型与能力判断时以当下官方文档和实际验证为准。

- **CLI agent** — 终端里派发任务，后台执行，结果以 diff 形式回审；部分团队的日常重心从 IDE 转到命令行。
- **IDE / 编辑器 agent** — 在编辑器内跨文件操作，配合实时 diff 与检查点。
- **云端 / 异步 agent** — 多个 agent 并行跑在不同分支或任务上，周期性查看而非持续盯守；工作节奏变成「派任务 → 审结果 → 再派」。
- **上下文基础设施** — 代码库索引、检索、MCP 连接器、项目约定文件，负责把大代码库的真实知识喂给 agent。
- **延伸实践** — spec-driven development（规格成为事实上的源，代码由 agent 从规格再生）、AI 审查常规 PR、以 Artifact（截图、录屏、测试结果）而非裸代码作为交付物。

## 7. 术语辨析

| 术语 | 含义 | 与 agentic coding 的关系 |
| --- | --- | --- |
| Agentic AI | 任何自主规划、执行、迭代复杂目标的 LLM 系统（客服、研究、金融等） | 上位概念；agentic coding 是它在软件工程上的实例 |
| AI-assisted coding | 补全、内联聊天等反应式辅助 | 对照物，主动权仍在人 |
| Vibe coding | 人的工作作风：用自然语言描述需求，几乎不审查底层代码就接受输出 | 描述的是审查强度，不是技术架构；agentic 工具既可以严谨使用，也可以 vibe 着用，两条独立的轴 |
| Agentic engineering | 把生产级工程纪律（可观测性、测试、版本控制、部署规范）施加到 agent 系统本身 | 成熟度更高的一层 |
| Spec-driven development | 规格为真源，实现由 agent 生成 / 再生 | agentic 工作流的一种组织方式 |

成熟度曲线常表现为：vibe coding → 有规格与审查的 agentic coding → 具备工程治理的 agentic engineering。

## 8. 固有局限

- **错误复利**：在自主循环中，一个误判会连续影响多步，等人看到时已放大。典型情形：改了 A 文件却未读到 B 文件的隐含假设；自己写实现又自己写测试，两者按同一误解一起通过；在某个失败用例上反复猜测，产出比原问题更难审的 diff。
- **上下文耗尽**：长任务累积工具输出，早期信息掉出窗口，agent 忘记做过什么。
- **规格歧义**：agent 会以同样的自信完成「不是本意」的任务，且不易自察。
- **权限外溢**：能执行命令就能误删、误推送；外部与不可逆动作必须留人工闸门。
- **同速不同险**：agent 处理支付迁移和改一行文案的速度与自信相同，审查强度必须按风险分级，而不是按产出大小。

结论：agent 越强，检查点与人工审查越不是可选项。
