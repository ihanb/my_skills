# Playbook — 委派流程、失败模式与团队落地

> 本文件是**委派流程、任务卡七字段、检查点、失败模式与验收命令的唯一事实源**。SKILL.md 只保留动作红线与流程骨架，字段命名一律以第 2 节表格为准。

## 1. 任务适配性判定

委派前先过这三项，任一不满足则先改造任务，而不是直接交给 agent：

- **可验证** — 存在机器能判定对错的信号（编译、测试、lint、接口响应、构建产物可启动）。纯审美、纯设计取舍不满足。
- **边界清晰** — 能列出涉及的文件 / 模块，以及明确「不做什么」。
- **可回滚** — 改动落在版本控制内，单个 diff 可独立 revert。

不整体委派的类别：架构决策、需求澄清、跨团队协调、生产环境变更、不可逆外部副作用（发消息、付款、删数据、强制推送）。这些可以拆出其中的「调研」或「起草」子步骤单独委派。

**与检查点的关系**：第 3 节的检查点用于**截断已委派任务中的错误复利**，不构成对上述类别的整体放行。即使每个外部动作都单独取得授权，也不把含不可逆副作用的任务整体委派；授权只作用于拆出来的子步骤。

## 2. 任务卡七字段

完整模板见 `assets/task-spec.md`。字段含义：

| 字段 | 要求 | 常见错误 |
| --- | --- | --- |
| 目标 | 一句话说明交付后的状态 | 写成动作（「优化一下代码」）而非状态 |
| 范围 | 列出允许改动的路径 / 模块 | 不写范围，导致 agent 顺手重构无关文件 |
| 不做的事 | 显式列出禁止项 | 缺失，agent 自行扩大范围 |
| 上下文入口 | 关键文件、约定文件、相关 issue、运行方式 | 让 agent 在大型仓库里盲搜 |
| 验收标准 | 可机器判定的命令与期望结果 | 用「合理」「优雅」「尽量」等形容词 |
| 权限边界 | 允许的命令类别、禁止的网络 / 外部动作 | 默认全开，误触不可逆操作 |
| 停止条件 | 重试上限、超时、何时必须转人工 | 不设上限，在失败用例上无限打转 |

模板分隔线之后的「检查点」「交付要求」「执行记录」是**附属区块**，不计入七字段；但审查与复盘需要，不应删除。

### 示例（合格的任务卡）

> 下方引用块只示意七个字段应写什么，不是可派发的格式；实际委派必须复制
> `assets/task-spec.md` 并逐项填写，否则无法机械校验。

> 目标：为 `/api/login` 增加基于 IP 的限流并补齐测试。
> 范围：仅 `src/middleware/rate_limit.*`、`src/routes/login.*`、`tests/test_rate_limit.*`。
> 不做的事：不改其他路由、不引入新依赖、不改数据库 schema。
> 上下文入口：现有中间件写法见 `src/middleware/auth.ts`；测试框架为 Jest，运行 `npm test -- --runInBand`。
> 验收标准：`npm run build` → 退出码 0；`npm test -- test_rate_limit` → 全绿；
> `npm test -- test_rate_limit_429` → 单 IP 第 6 次请求返回 429 的用例通过。
> 权限边界：只读 + 本地文件写入 + 本地测试命令；禁止 git push、禁止访问网络。
> 停止条件：同一失败重试不超过 3 轮；超过则停止并列出已尝试方案与剩余疑点。

### 静态校验

两类产出物都必须过校验器（零依赖，脚本定位方式见 `SKILL.md`「脚本定位」一节）：

- 任务卡：`python "<SKILL_ROOT>/scripts/check_spec.py" <任务卡路径>`
- 审查记录：`python "<SKILL_ROOT>/scripts/check_spec.py" <记录路径> --kind review`

任务卡校验七字段齐全、占位符已替换、验收标准**每条**都是「反引号命令 + 同行期望输出」（纯文字的「边界行为：xxx」会被拦截）、禁止项与重试上限非空；验收标准含模糊形容词直接判 ERROR，目标含模糊词告警，「禁止：无」按空值拦截。审查记录校验七项齐全、结论（合并 / 打回 / 转人工）与风险级别（低 / 中 / 高）取值合法。**只有 PASS 才可委派 / 才算完成审查**；`--strict` 会把 WARN 也视为失败。

## 3. 检查点设计

在以下时机要求 agent 暂停并等待确认：

- 产生跨模块 / 结构性改动之后；
- 安装新依赖、修改构建配置之前；
- 任何不可逆或外部命令之前（push、部署、发消息、删除、覆盖）；
- 验收标准本身需要调整时（说明规格有歧义，应由人裁决）；
- 连续两轮验证失败之后。

检查点的作用是截断错误复利，不是降低自动化程度；适用范围见第 1 节的边界说明。

## 4. 失败模式与缓解

| 失败模式 | 表征 | 缓解 |
| --- | --- | --- |
| 规格歧义 | 交付物「技术上完成」但不是本意 | 把验收标准写成可判定命令；先让 agent 复述理解再动手 |
| 自证式通过 | 实现与测试共享同一误解 | 测试由人给用例或独立生成；关键路径加人工设计的边界用例 |
| 无限重试 | 同一失败上反复猜测，diff 越改越乱 | 设 3 轮上限；超限回滚到最近干净状态并转人工 |
| 上下文膨胀 | 长任务后忘记早期决策、重复改动 | 分段交付；每轮结束写简短状态摘要；保持项目约定文件精简 |
| 跨文件破坏 | 改 A 破坏 B 的隐含假设 | 范围字段限定路径；审查时按依赖方向检查调用方 |
| 范围蔓延 | 顺手重构、格式化无关文件 | 「不做的事」字段 + 审查首项即过滤 diff 范围 |
| 权限外溢 | 误 push、误删、误发外部请求 | 白名单命令；外部动作单独授权；沙箱或分支隔离 |
| 同速不同险 | 高危改动与文案改动被同等对待 | 按风险分级决定审查强度（见 `references/review-checklist.md` 第 3 节） |

## 5. 上下文管理

- 在项目根维护简短的约定文件（构建命令、目录职责、代码规范、禁止事项），让 agent 每轮都能重新对齐，而不是依赖会话记忆。
- 给任务卡提供精确的文件入口，避免全仓扫描消耗窗口。
- 长任务按「一个可验证目标 = 一轮」切分，每轮结束产出状态摘要，下一轮从摘要续接。
- 控制工具输出体量：只回读失败片段、精简日志、避免把整份大文件反复灌入上下文。

## 6. 按技术栈确定验收命令

验收标准必须落在本栈**真实可执行**的命令上。以下只是常见栈的示意，**按实际项目替换**，并以项目约定文件、CI 配置中的命令为准：

- C++ / CMake：`cmake --build <dir>`、`ctest --test-dir <dir>`；桌面端还需验证部署脚本与运行时依赖齐全、产物可启动。
- Rust / Tauri：`cargo check`、`cargo test`、`cargo clippy`、前端 `build` 与桌面端启动。
- Java / Spring Boot：`mvn test` 或 `gradle test`、应用启动后关键接口探测。
- 前端 / Node：`build`、单测、lint、必要时浏览器截图核对 UI 行为。
- 多语言混合链路：至少验证跨进程边界（HTTP 接口、DLL 调用、IPC），不要只验证各自单元测试。

## 7. 团队落地与度量

- 从小任务起步，先建立「任务卡 + diff 审查」的习惯，再扩大委派范围。
- 要求每个 agent 产出的 PR 附带任务卡链接与验收命令输出，使审查有据可查。
- 度量关注：返工率、审查发现的缺陷密度、diff 平均规模、超限转人工次数；不单纯以「生成代码行数」或「任务耗时」衡量收益。
- 建立偏差回写机制：把常见的规格歧义沉淀成模板字段或项目约定，形成可复利的知识资产。
- 明确底线：agent 可以修编译器与测试发现的问题，但代码库风格、隐含业务逻辑、生产风险判断仍由人负责。
